# Rider Comms product and engineering audit

Audit date: 2026-09-15

This audit follows the PWA product-polish pass. It distinguishes verified work
from production dependencies that are not present in the repository. The PWA
is now a substantially stronger test surface, but Rider Comms is not ready for
public release or store submission.

## Findings

### 1. Durable accounts and data

- **Issue:** Authentication, profiles, rides, friendships, messages and presence are held in process memory.
- **Severity:** Critical
- **Affected area:** Backend, all clients
- **Affected platforms:** PWA, iOS, Android
- **Current behaviour:** Restarting the API removes sessions and product data. The static PWA uses device-local demonstration state and is not connected to this API.
- **Expected behaviour:** Durable accounts, revocable sessions, consistent cross-device state, migrations, backup and deletion controls.
- **Recommended solution:** Add a production database and object storage, migrate every store behind repository interfaces, add session expiry/revocation, and connect the PWA to the authenticated API.
- **Estimated complexity:** Large
- **Dependencies:** Database, hosting, data model, privacy/retention policy
- **Risks:** Data loss, account loss, inconsistent identities and misleading test results if released as-is.

### 2. Billing is not transaction-ready

- **Issue:** There are no App Store, Play Store or web billing products and no server receipt validation.
- **Severity:** Critical
- **Affected area:** Subscription and entitlement system
- **Affected platforms:** PWA, iOS, Android
- **Current behaviour:** The redesigned UI shows the backend-owned Free entitlement and locked paid plans; purchase actions state that purchasing is unavailable. No tier can be unlocked locally.
- **Expected behaviour:** Provider-appropriate checkout, verified receipts/webhooks, restore, reconciliation, refunds, upgrades, downgrades and management links.
- **Recommended solution:** Define products and entitlement rules, implement server verification first, then StoreKit/Play Billing for native and an allowed web provider for the PWA.
- **Estimated complexity:** Large
- **Dependencies:** Apple/Google developer accounts, legal business details, billing provider, durable database
- **Risks:** Store rejection, lost revenue and entitlement fraud.

### 3. Native Google Maps is not configured

- **Issue:** Google Maps is supported in the PWA deployment but the Expo client still renders an illustrative SVG map.
- **Severity:** High
- **Affected area:** Native map and navigation
- **Affected platforms:** iOS and Android
- **Current behaviour:** The PWA loads Maps JavaScript using a deployment-injected, referrer-restricted key and falls back safely. Native uses foreground GPS but no native map SDK.
- **Expected behaviour:** Platform-native Google Maps rendering, real rider coordinates, route display, selection, clustering and tested failure states.
- **Recommended solution:** Add `react-native-maps` (or an approved navigation SDK), use dynamic Expo app configuration for separate restricted iOS/Android keys, and implement a shared marker/view-model layer.
- **Estimated complexity:** Large
- **Dependencies:** Google Cloud project, billing, bundle IDs/package names, native development builds, location threat model
- **Risks:** Key abuse, cost spikes, store privacy disclosures and cross-platform divergence.

### 4. Group Ride realtime isolation is incomplete

- **Issue:** The API isolates ride membership but has no realtime ride chat or location subscription layer.
- **Severity:** High
- **Affected area:** Group Ride
- **Affected platforms:** All
- **Current behaviour:** The PWA now keeps public rider data and private ride roster data in separate state paths and resets selection when a ride changes. Native polls the ride roster. There are no realtime channels to prove unsubscribe/resubscribe behaviour.
- **Expected behaviour:** Ride-scoped messages, presence and coordinates with membership authorization, explicit channel teardown, reconnection and multi-user tests.
- **Recommended solution:** Define ride channel identifiers and authorization claims, add websocket/realtime infrastructure, and integration-test switching, leaving, removal, ending and reconnecting with multiple actors.
- **Estimated complexity:** Large
- **Dependencies:** Durable membership store, realtime service, test harness
- **Risks:** Cross-ride privacy leaks and stale rider state.

### 5. Public rider coordinates are not a complete product API

- **Issue:** Presence returns rider identifiers but not privacy-safe position/status summaries.
- **Severity:** High
- **Affected area:** Map, privacy, presence
- **Affected platforms:** All
- **Current behaviour:** PWA marker positions are demonstration data; native explicitly lays riders out illustratively.
- **Expected behaviour:** Authorized, time-bounded coordinates with precision rules, freshness, heading and status.
- **Recommended solution:** Create a privacy-reviewed presence response, quantize precision where appropriate, expire aggressively, disclose sharing clearly, and never log raw coordinates by default.
- **Estimated complexity:** Medium
- **Dependencies:** Threat model, database/realtime architecture, map SDK
- **Risks:** Location stalking, misleading map state and regulatory exposure.

### 6. Visual verification coverage is missing

- **Issue:** No automated responsive screenshot, overflow or accessibility suite exists.
- **Severity:** High
- **Affected area:** Release quality
- **Affected platforms:** Small/large phones, tablets, landscape, installed PWA
- **Current behaviour:** CSS uses safe-area variables, dynamic viewport units, compact breakpoints, width constraints, large-display layouts and reduced-motion handling. Syntax/build/native bundles pass. The managed browser could not access the local test server, so visual browser verification was not marked as passed.
- **Expected behaviour:** Repeatable browser tests across representative viewports plus VoiceOver/TalkBack/manual device checks.
- **Recommended solution:** Add Playwright visual and interaction tests in CI, include viewport and text-scaling matrices, and run a physical-device acceptance checklist before every candidate build.
- **Estimated complexity:** Medium
- **Dependencies:** Browser test infrastructure and baseline approval
- **Risks:** Undetected clipping, keyboard obstruction and platform-specific regressions.

### 7. PWA and native remain separate UI implementations

- **Issue:** The deployed PWA is a static application while the authenticated product client is React Native/Expo.
- **Severity:** High
- **Affected area:** Frontend architecture
- **Affected platforms:** PWA versus native
- **Current behaviour:** The PWA now has a coherent consumer UI and reliable deployment but duplicates product state and interactions.
- **Expected behaviour:** Shared API models, design tokens, identity components and behavioural tests, ideally a single web-capable application where practical.
- **Recommended solution:** Decide whether Expo Web becomes the production PWA or retain a separate web client intentionally; then share generated API types and design tokens and remove duplicated demonstrations.
- **Estimated complexity:** Large
- **Dependencies:** Product/platform strategy, Expo Web compatibility, map strategy
- **Risks:** Feature drift and inconsistent user expectations.

### 8. Voice and moving-state safety controls are incomplete

- **Issue:** Audio rooms, VOX, Bluetooth behaviour and authoritative movement lockouts do not exist.
- **Severity:** Critical
- **Affected area:** Core communications and safety
- **Affected platforms:** iOS and Android
- **Current behaviour:** Audio priority algorithms exist. The product copy discourages visual tasks while moving, but posting/social features and motion detection are not implemented.
- **Expected behaviour:** Tested voice-first controls and a conservative moving-state policy that blocks video creation/upload interaction while moving without blocking emergency or navigation access.
- **Recommended solution:** Implement voice infrastructure, derive movement from platform motion/location signals with false-positive handling, define passenger override policy, and validate on real helmet/Bluetooth hardware.
- **Estimated complexity:** Large
- **Dependencies:** LiveKit/service credentials, native modules, safety research, physical testing
- **Risks:** Rider distraction, false lockouts and unreliable emergency behaviour.

### 9. Social video and scenic routes are product concepts, not implemented services

- **Issue:** Feed uploads, public/friends visibility, moderation and vehicle-suitable route discovery require backend and policy foundations.
- **Severity:** Medium
- **Affected area:** Product expansion
- **Affected platforms:** All
- **Current behaviour:** Profile Instagram/TikTok fields and visibility controls exist. No media feed or route catalogue exists.
- **Expected behaviour:** Moderated, storage-backed media with audience enforcement; curated/rated routes with vehicle attributes, safety notices and filters.
- **Recommended solution:** Treat these as separate epics after identity/storage. For video, build audience authorization at query/storage level and stationary-only creation UX. For routes, define provenance, suitability taxonomy, hazards and map provider terms before building the tab.
- **Estimated complexity:** Large
- **Dependencies:** Accounts, object storage/CDN, moderation, maps/routes data, legal policy
- **Risks:** Unsafe content, privacy leakage, high storage cost and unsuitable-route liability.

### 10. Delivery-app navigation handoff needs platform integration

- **Issue:** Rider Comms is not registered as a navigation destination/provider for Uber, Deliveroo or system share flows.
- **Severity:** Medium
- **Affected area:** Navigation interoperability
- **Affected platforms:** iOS and Android
- **Current behaviour:** No deep-link or intent handling exists.
- **Expected behaviour:** Supported apps can hand an address/coordinate to Rider Comms, and Rider Comms can open an installed navigation provider.
- **Recommended solution:** Implement universal/app links and Android intent filters for coordinate/address payloads, document supported schemes, and avoid claiming first-party Uber/Deliveroo integration without their partnership/API support.
- **Estimated complexity:** Medium
- **Dependencies:** Native routing, domain association files, map/navigation SDK, partner capabilities
- **Risks:** Store-policy problems, malformed intents and misleading interoperability claims.

## Prioritised roadmap

### P0 — must fix before release

1. Durable accounts, database, revocable sessions and cross-client data deletion.
2. Real provider-verified billing and entitlement reconciliation.
3. Location privacy threat model and authorized presence payloads.
4. Voice/movement safety implementation plus real-device testing.
5. Realtime Group Ride isolation and multi-user privacy tests.

### P1 — high priority

1. Native Google Maps/navigation and platform-specific key configuration.
2. Decide and execute a unified PWA/native frontend strategy.
3. Automated responsive, accessibility and installed-PWA test matrix.
4. Production observability, incident response, backups and abuse tooling.

### P2 — product and UX improvement

1. Real avatar upload/crop/cache propagation.
2. Universal links, shareable ride links/QR and supported navigation handoff.
3. Motion polish after performance and reduced-motion validation.
4. Social video foundation with friends/public audience enforcement.

### P3 — longer-term enhancement

1. Curated scenic-route catalogue, suitability filters and community quality signals.
2. Partner integrations with delivery/mobility providers where officially supported.
3. Advanced clustering, heading, convoy progress and route hazard intelligence.

## Follow-up: visual/interaction verification (2026-09-15, continued)

Finding 6 above noted that browser-based visual verification had not been run
against a live local server. That gap is now closed: the PWA was built,
served locally alongside the backend, and driven with Playwright across
320/375/390/430px, a common Android width (360px), tablet portrait/landscape,
and a wide desktop width, capturing all four screens (Map, Group Ride,
Friends, Settings) at each size, plus scripted interaction tests (create/join/
end a ride, edit profile including Instagram/TikTok/visibility, accept/
decline a friend request, open the billing sheet).

This surfaced and fixed three real defects, not just cosmetic gaps:

- **Broken settings icon markup.** The gear icon's hand-authored SVG `path`
  data was malformed and threw a browser rendering error on every screen
  (`<path> attribute d: Expected number...`). Replaced with a validated
  icon path. This was a genuine bug, not a false positive — it fired on
  every page load at every viewport tested.
- **A real (if narrow) public/private ride isolation leak.** `docs/app.js`'s
  Google-Maps marker click handler always looked up the tapped rider in the
  *public* roster (`PUBLIC_RIDERS`) regardless of ride state, instead of the
  ride-scoped roster the fallback (no-API-key) marker path already used
  correctly. With the shared fixture data this mostly self-masked, but it is
  exactly the "public rider data leaking into private ride context" failure
  mode called out as a risk elsewhere in this document, and it would have
  been live wherever a real Google Maps key is configured. Fixed to use the
  same ride-aware roster both rendering paths already agree is correct.
- **Incomplete desktop-sidebar removal.** PR #32 was meant to remove the
  desktop sidebar layout, but instead of deleting it, it added a second,
  later `@media(min-width:1080px)` block that overrides the first one back
  to a centered mobile layout. The result was visually correct (verified
  again here) but relied on CSS cascade order between two blocks targeting
  the same breakpoint — a fragile setup that a future edit could silently
  break. Removed the original sidebar block and its now-unused
  `<aside class="desktop-brand">` markup entirely rather than leaving a
  second block to keep overriding it.

With those fixed, a second full pass (screenshots + interactions) showed zero
console errors across every viewport and confirmed: public riders correctly
disappear from the map for the duration of a private Group Ride and
correctly reappear once it ends; profile edits (display name, handle,
Instagram, TikTok, social visibility) persist correctly; and the billing
sheet's copy never claims a purchase is active — it explicitly states
purchases are unavailable.

## Follow-up: native/PWA copy and architecture consistency (2026-09-15, continued)

Finding 7 above (PWA and native remain separate UI implementations) is a
real, unresolved architectural gap and is not closed by this pass. Within
that constraint, one smaller but concrete inconsistency was fixed: the PWA
audit had already removed user-facing developer language ("TODO", "not
wired up") from its copy, but the native Expo screens still showed literal
"TODO" text to end users in three places (`FriendsScreen.tsx`'s own-rider-ID
share caption and add-friend caption, `FriendChatScreen.tsx`'s hideout
map-picker caption). Reworded all three to normal product copy and moved the
developer-facing detail into code comments, matching the convention already
used on the web side.

`BillingScreen.tsx`'s payment TODO comment was also expanded: it previously
implied the remaining work was "swap in a real processor" (i.e. wire up
Stripe-style tokenization). That underspecifies the actual constraint for a
native iOS/Android subscription: the production path is StoreKit and Google
Play Billing, not a generic card processor, which App Store/Play Store
review does not allow for this kind of in-app digital subscription. The
mocked card-entry UI (brand/last4/expiry) is a stand-in for "you have a
payment method on file," not a preview of the real checkout UI — the actual
implementation replaces that UI shape entirely with each store's native
purchase sheet, with the backend verifying the resulting receipt/token
server-side. This is now stated explicitly in the code comment so it isn't
mistaken for a smaller task than it is.

## Follow-up: backend hardening merged (2026-09-15, continued)

A separate, independently-authored PR (`codex/enterprise-api-foundation`,
merged as PR #29) added exact-origin CORS enforcement with preflight
support, request IDs, structured JSON request logs, a `/ready` readiness
endpoint, defensive response headers (CSP, frame-ancestors, referrer
policy, etc.), and graceful `SIGTERM`/`SIGINT` shutdown to the backend. It
was inspected for conflicts against the current `main` (none — it touches
only `backend/src/server.ts`, its tests, `README.md`, and `.env.example`),
validated locally (`npm run check`, `npm run build:web`), confirmed green
on CI, and merged. This closes part of the "production observability" gap
in the P1 roadmap above (structured logs and a readiness probe now exist)
but does not by itself provide metrics, alerting, or a durable database —
those remain open per Findings 1 and 6.
