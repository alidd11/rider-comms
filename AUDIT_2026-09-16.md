# Rider Comms audit — search screen + full-app pass

Audit date: 2026-09-16

This audit covers two things: the search screen shipped in PR #108
("Improve search screen UX to match Google Maps/Waze patterns"), and a
full-repository pass (automated tests, mobile builds, PWA compliance)
requested separately. It follows the same evidence-based method as
`AUDIT_2026-09-15.md` — driving the real app with Playwright and reading
the actual console/network output, not just reading the diff.

## Method

- Built the PWA (`npm run build:web`) and served it from a local static
  server.
- Ran the backend locally against a real local Postgres instance (the
  deployed backend enforces an exact-origin CORS allowlist that a
  throwaway local origin isn't on, so this was required to exercise
  signup/login and the friend/search flows at all).
- Signed up a disposable test account and drove the app with headless
  Chromium (Playwright): auth → map → search screen (empty state, typing,
  results, clear button, recent list, select) → Ride/Routes/Friends/
  Settings tabs, capturing a screenshot at every step and recording every
  console message and page error.
- The production Google Maps JS key is HTTP-referrer-restricted to the
  real deployed origin, so it renders tiles and answers Places requests
  only from that exact origin — not from a local test server. To still
  exercise the search screen's own rendering logic (icons, distance,
  recent list, loading state), `AutocompleteService.getPlacePredictions`
  and `PlacesService.getDetails` were mocked with deterministic fixture
  data after confirming the real key/referrer restriction was the actual
  blocker (not a bug). Everything downstream of that mock — DOM
  rendering, the destination card, recent-search persistence — is real
  app code exercising real app code paths, not simulated.
- Ran the full test/type/lint suite (`npm run check`), and the mobile
  app's `expo-doctor` and `expo export` for both platforms.

## Findings

### 1. Recent-search selection crashed with an uncaught TypeError — fixed

- **Severity:** Critical (this exact path, shipped in PR #108)
- **Repro:** Search for a place → select a result (saves it to Recent) →
  reopen search → tap that Recent entry.
- **Cause:** `selectRecentSearch()` passed a plain `{lat, lng}` literal
  into `setDestinationMarker()` → `showDestinationCard()`, which calls
  `location.lat()`/`location.lng()` as *methods* — correct for the real
  `google.maps.LatLng` the live-search path provides via
  `PlacesService.getDetails()`, but not for a plain literal. Every tap on
  a Recent entry threw `location.lat is not a function` and the
  destination card never appeared.
- **Fix (pushed to PR #108):** wrap the stored coordinates in a real
  `google.maps.LatLng` before handing them to the shared card code.
  Verified with Playwright: selecting a Recent entry now drops the pin,
  shows the destination card, and throws nothing.

### 2. Destination card overlapped the floating map buttons and truncated its own text — fixed

- **Severity:** High (pre-existing, but PR #108's search feature is what
  makes it common — place names are longer and more varied than the
  rider names this card was originally designed to show)
- **Repro:** Search for a place with a name longer than a couple of
  words (e.g. "Shell Petrol Station") and select it.
- **Cause:** `#destinationCard` shares the generic `.rider-card` CSS
  (centered, `width: min(100% - 32px, 420px)`) with the plain rider info
  card and the hazard card — but it's the only one of the three with
  three trailing controls (Start / share / dismiss) instead of one. At
  that width and content, its right edge reached under the fixed
  `.map-actions` button column (hazard-alert / recenter / offline
  toggle), and the copy area left for the place name and address was so
  narrow that both were ellipsis-truncated to a couple of characters
  ("Shell P…", "51.50000, -…"). It also only ever showed raw
  coordinates, never the place's real address, even though
  `selectSearchResult()` already fetches `formatted_address`.
- **Fix (pushed to PR #108):**
  - `showDestinationCard`/`setDestinationMarker` now take the place's
    real address and show it instead of coordinates.
  - `#destinationCard` got its own two-row layout (name/address on one
    row, the three controls on the row below) inset from the button
    column, instead of sharing the single-row layout that only fits the
    simpler cards. Verified with a screenshot: full readable name and
    address, no overlap, and a wider, easier-to-tap Start button as a
    side effect.
- **Not changed:** the plain rider-info card and hazard card, which only
  have one trailing control each and were never actually broken.

### 3. Search screen itself — no other defects found

With the above two fixed, the rest of the feature checked out clean
end-to-end: empty-state hint vs. recent list, the clear (×) button
appearing/disappearing correctly, the "Searching…" loading state,
per-place-type icons on result rows (fuel/parking/food/coffee), Escape
closing the screen, and POI chips still opening the map with dropped
pins. Zero console errors or page errors attributable to app code across
the whole run (see below for the ones that were pre-existing/unrelated).

### 4. Route images hotlink Wikimedia Commons directly and get rate-limited

- **Severity:** Medium (reliability, and a real risk of Wikimedia
  blocking this app's traffic outright, not just slowing it down)
- **Affected area:** Routes tab, unrelated to PR #108
- **Evidence:** During this same run, every route card's image request
  to `commons.wikimedia.org/wiki/Special:FilePath/...` came back `429`,
  with a body that isn't a generic rate limit — it's Wikimedia's own
  abuse notice: *"please contact noc@wikimedia.org to discuss a less
  disruptive approach or instead use thumbnail images in sizes listed on
  https://w.wiki/GHai"*. That is the response Wikimedia gives integrators
  it considers to be hotlinking disruptively, not ordinary throttling.
  `docs/routes.js` builds these URLs itself
  (`commons.wikimedia.org/wiki/Special:FilePath/${file}?width=1280`) at
  render time, for every visitor, with no caching layer in front of it —
  this will happen in production too, not just in this sandboxed test.
- **Not fixed here:** this needs a real decision (self-host the already
  CC-licensed images per `ROUTE_IMAGE_LICENSES.md`, or switch to
  Wikimedia's actual thumbnail API at the sizes they publish) rather than
  a quick patch, and it's unrelated to the search-screen PR. Flagging it
  because "run a full audit to ensure no errors" surfaced it directly.

### 5. Minor PWA/mobile compliance items — fixed or noted

Checked the PWA against current web-app-installability criteria and
both platforms' current App Store / Play Store guidance:

- **Fixed:** Chrome's console flags the Apple-only
  `apple-mobile-web-app-capable` meta tag as deprecated on its own and
  expects the standard `mobile-web-app-capable` tag alongside it (a real
  warning observed live in this run, not a guess). Added the standard
  tag; kept the Apple one, since iOS Safari still requires it.
- **Already compliant, verified against current guidance:**
  `manifest.json` has both required icon sizes (192/512, with maskable
  variants — a nice-to-have, not just the minimum), `short_name`,
  `start_url`, and a valid `display` value; served over HTTPS. Meets
  Chrome/Android's installability bar as published today.
  `NSLocationWhenInUseUsageDescription` and
  `NSMicrophoneUsageDescription` in `mobile/app.json` both clearly state
  purpose, matching Apple's 5.1.5 requirement; in-app account deletion
  (required by Apple 5.1.1(v) whenever an app supports account creation)
  is already implemented per `COMPLIANCE.md`.
- **Noted, not fixed (routine drift, not a defect):** `expo-doctor`
  reports `expo` and `expo-location` are one patch version behind the
  installed Expo SDK's expected range (57.0.22 vs 57.0.23, 57.0.17 vs
  57.0.18). Fix with `npx expo install --check` when convenient; nothing
  in this audit depended on those patches.
- **Reconfirmed, not new:** Rider Comms is still fundamentally a
  pre-alpha test build by Apple's and Google's own submission
  definitions (2.1(a): "final versions", no placeholder/backend-less
  content; Play's Data Safety and deletion-mechanism requirements assume
  a durable account system). `COMPLIANCE.md`'s existing list of blockers
  before public submission (durable accounts/database, real billing,
  moderation staffing, physical-device and store-account setup) is still
  accurate as of this pass — nothing found here changes that.

## Verification

- `npm run check` (lint + typecheck + tests): 228 tests across 49 suites
  (77 shared, 119 backend, 32 mobile client), **0 failures**.
- `npx expo-doctor`: 20/21 (the one failure is the patch-version drift in
  Finding 5, not a functional issue).
- `npx expo export --platform ios` and `--platform android`: both
  succeed.
- `git diff --check`: clean.
- Playwright end-to-end run against a locally-hosted build + local
  backend: 0 console errors or page errors attributable to app code,
  after fixing Findings 1–2. Screenshots captured for every screen and
  every search-screen state.

## What this audit does not cover

- Real (non-mocked) Google Places network responses — blocked by the
  production key's referrer restriction from any origin other than the
  deployed one; this is correct, expected key configuration, not a gap
  to fix. The mock only stands in for that one network call; everything
  it triggers downstream is real app code.
- Physical-device testing (VoiceOver/TalkBack, real GPS, real Bluetooth
  headsets, actual App Store/Play Store review) — out of scope for an
  automated pass, and already called out as an open requirement in
  `COMPLIANCE.md`.
