# Rider Comms full product, engineering and UX audit

**Audit date:** 17 September 2026

**Audited revision:** `1cd642681454a138a2b7180221a693b83b7b19bc` (`main`)

**Scope:** all tracked source, tests, configuration, workflows and product documentation in the repository; PWA behavior at four viewport classes; native static validation and iOS/Android export.

This is an improvements-only report. It does not repeat completed work as open work, and it does not treat an external production prerequisite as if it were an implemented feature.

## Executive assessment

The repository is materially healthier than it was at the 15 September audit. The current code passes its lint, type, unit, client, browser-smoke and Expo checks. The PWA bottom navigation now renders consistently on first load, stays above the home indicator and does not overflow at the tested sizes. Native maps now use real coordinates. Search has typed category queries and defensive distance filtering. Profiles, friend requests, direct messages, reporting and blocking are connected to durable stores.

The product is still not ready to make its central hands-free riding promise. The highest-risk gap is no longer basic screen polish: it is that the tested movement-safety model is not connected to either client, while voice/audio functionality remains incomplete. A rider can still reach ordinary interactive controls while moving, public voice deliberately fails closed, and computed audio priorities are not applied to real streams.

The next engineering milestone should therefore be a safety-and-audio milestone, not more surface-area expansion.

## Detailed findings

### 1. P0 — Connect the movement safety system to the product

`shared/src/movementState.ts` contains a carefully tested tracker with accuracy filtering, hysteresis, stale-fix handling and a fail-locked `isLockedForSafety()` decision. Repository-wide reference search finds it only in its implementation, tests and the previous audit. Neither client supplies live fixes to it or uses its output to restrict interaction.

**Improve by:**

1. Create one client adapter per platform that converts OS fixes into `{ lat, lon, timestampMs, accuracyMeters }`.
2. Keep `unknown` and `moving` locked; unlock only after the tracker's stationary confirmation period.
3. Replace complex interactive screens with a minimal, high-contrast ride-safe surface while locked.
4. Keep emergency actions, spoken status and stop-ride controls accessible.
5. Add deterministic integration tests for cold start, GPS loss, poor accuracy, background/foreground and movement-to-stop transitions.
6. Validate on physical devices and real rides; simulator traces alone are insufficient.

### 2. P0 — Finish voice, audio mixing and system controls

The backend deliberately returns `public_voice_unavailable` for public voice. `mobile/src/audio/audioEngine.ts` computes gains but has a native TODO where those gains must be applied. `mobile/src/audio/nowPlayingBridge.ts` throws for play, pause and skip because no media-session binding exists. That means the architecture expresses the intended priority (`navigation > chat > music`) without delivering it to actual audio streams.

**Improve by:**

- Authorise public-channel membership server-side before minting LiveKit tokens.
- Bind LiveKit publication/subscription state to the existing privacy and block model.
- Apply gain changes to real navigation, chat and music sessions, including interruption recovery.
- Implement iOS `MPRemoteCommandCenter` and Android media-session controls through a supported native module.
- Add Bluetooth route-change, phone-call, screen-lock, background, reconnect and packet-loss tests.
- Make disconnect and mute state audible/haptic so the app remains usable without looking at the screen.

### 3. P0 — Add the missing production operating system around the app

Durable product stores and atomic account deletion are now present, but the repository correctly documents that production operations are not complete. There is no user password-reset flow, automated retention/deletion schedule, demonstrated encrypted backup/restore process, production monitoring/alerting evidence, incident runbook or staffed moderation process.

**Improve by:**

- Add one-time, short-lived password-reset tokens with enumeration-safe responses, rate limiting and session revocation after reset.
- Convert the retention policy into scheduled deletion jobs with auditable outcomes.
- Configure encrypted backups and complete a recorded restore drill before launch.
- Add service, queue, database, map/search and voice SLOs with paging thresholds.
- Define moderation response times, escalation ownership and evidence-retention rules.
- Run a data-protection/legal review for precise and inferred location data.

### 4. P0 — Implement real billing and entitlement enforcement

Plan names and radii are represented in the UI and profile model, but there is no provider checkout, store purchase, receipt validation, webhook reconciliation, refund handling or server-owned entitlement ledger.

**Improve by:**

- Choose App Store/Play billing and a compliant web billing path.
- Treat verified server entitlements as authoritative; never trust a client-selected tier.
- Make webhook processing idempotent and replayable.
- Test upgrade, downgrade, expiry, grace, refund, restore-purchase and cross-device cases.
- Remove or clearly label purchasable-looking UI until the complete flow is available.

### 5. P1 — Validate location evidence and make presence genuinely scale-safe

Both clients send latitude and longitude only. The `/presence` endpoint validates numeric coordinate bounds, then trusts the point and stamps it with server time. It receives no accuracy, fix timestamp or movement evidence, so spoofed or stale points can affect zone matching.

There is also a mismatch between comments and implementation in `PresenceStore`: `zoneCandidates()` calls `loadAllRiders()` and filters buckets in application memory, while stale pruning also loads the entire table. The database schema has no persisted bucket/spatial index. `previousPairs` is process-local, so multiple backend instances can calculate inconsistent entered/left transitions.

**Improve by:**

- Send accuracy and fix timestamp; reject stale or unreasonably inaccurate fixes.
- Apply conservative speed/distance plausibility checks without silently creating surveillance history.
- Persist an indexed bucket (or use PostGIS) and query only neighbouring buckets in SQL.
- Delete stale rows with one indexed database predicate instead of loading all riders.
- Derive transitions from durable state or a shared event/cache layer so instances agree.
- Load-test realistic urban density, reconnect storms and multiple backend replicas.

### 6. P1 — Replace repeated polling with a scoped realtime transport

The native Ride context polls every five seconds; Friends and direct-message screens also poll. The PWA polls presence, ride location and hazards. This delays chat and roster changes while repeatedly waking the device radio and backend.

**Improve by:**

- Use authenticated, ride/user-scoped WebSocket or realtime subscriptions.
- Keep a slower, jittered poll as recovery rather than the primary transport.
- Specify sequence IDs, deduplication, missed-event replay, reconnect backoff and unsubscribe behavior.
- Suspend nonessential work in the background and resume with a single catch-up sync.
- Measure battery, data and backend connection costs on representative phones.

### 7. P1 — Harden PWA authentication storage and content policy

The native client stores its session in Expo SecureStore. The PWA stores the bearer token in `localStorage`, where any successful same-origin script injection can read it. The backend sends defensive API headers, but the GitHub Pages PWA cannot configure equivalent response headers and currently has no meta CSP.

**Improve by:**

- Prefer a short-lived access token plus a rotating, `HttpOnly`, `Secure`, `SameSite` refresh cookie on an application origin that can set security headers.
- If static hosting is retained temporarily, minimise token lifetime and add a strict CSP compatible with the exact Google Maps/font origins and required script behavior.
- Remove inline-script requirements before enforcing CSP and add automated policy regression checks.
- Add explicit remote-session revocation/device-session management.

### 8. P1 — Make environment boundaries explicit

`docs/app.js` hardcodes `https://backend-production-7fa0.up.railway.app`. The map key is deployment-configured, but the API base is not. Local previews and branch builds therefore point at production unless code is changed.

**Improve by:**

- Put `apiBaseUrl` in generated `config.js` alongside the maps configuration.
- Maintain development, staging and production allowlists and credentials.
- Fail a production build if it contains a development origin, and fail preview builds if they point at production without an explicit override.
- Display the environment in non-production builds and seed staging with synthetic accounts only.

### 9. P1 — Reduce duplicated client behavior

The PWA is a hand-built JavaScript application while native is React Native. API calls, polling, location behavior, search orchestration, auth messaging and screen state are implemented twice. Shared pure logic helps, but the behavior boundary is still too wide.

**Improve by:**

- Move request/response schemas, validation, error mapping, location policy and state machines into shared typed modules.
- Add contract tests that run the same scenarios against PWA and native adapters.
- Share design tokens and interaction specifications even where renderers remain separate.
- Define parity explicitly: which PWA capabilities are previews, which are production-equivalent, and which require native OS APIs.

### 10. P2 — Turn the visual smoke suite into a release-quality UX gate

The new suite is valuable: all 24 screenshots rendered without local page errors or horizontal overflow. It does not compare screenshots to approved baselines, run WebKit, exercise keyboard/large-text behavior, test offline/service-worker upgrades or render native screens.

**Improve by:**

- Add reviewed visual baselines and thresholded diffs for the six core screens.
- Add WebKit mobile emulation for Safari-specific safe-area and viewport behavior.
- Add automated accessibility checks plus manual VoiceOver/TalkBack passes.
- Test 200% text, reduced motion, high contrast, software keyboard and smallest supported screen.
- Add offline-first launch, stale service worker, interrupted update and recovery scenarios.
- Capture physical iPhone and Android screenshots for each release candidate.

### 11. P2 — Give navigation a rider-specific reason to exist

The current app can show real coordinates, search places and hand a destination to an external maps app. That is useful plumbing, but it does not compete with mature turn-by-turn products and should not be presented as though it does.

**Improve by:**

- Focus the in-app experience on differentiated rider value: spoken community hazards, group rendezvous context, route suitability and low-distraction handoff.
- Make the primary destination action explicit: preview, share with ride, or open in the user's navigation app.
- Add arrival/rejoin-group flows rather than duplicating general road navigation.
- Defer claims about background guidance, rerouting, traffic or provider integration until those behaviors are implemented and tested.

### 12. P2 — Use landscape space intentionally

The screenshot matrix shows no overflow, but Search, Ride and Friends remain narrow centered columns in phone landscape with large unused areas. Routes is more effective because it switches to multiple visible cards. Search also presents its permission/error state as a centered block rather than using the map context or a results pane.

**Improve by:**

- Use a split layout in landscape: compact controls/results on one side, map or ride context on the other.
- Keep bottom navigation compact but preserve the safe-area inset.
- Show useful search recovery inline: current permission state, how to enable it and a manual area/address fallback.
- Avoid stretching phone layouts on tablets; set purposeful maximum widths and multi-column content where scanning benefits.

### 13. P2 — Remove remaining single-instance and external-asset assumptions

`SlidingWindowRateLimiter` is explicitly in memory, so limits reset on restart and are multiplied across replicas. Presence transition state is also process-local. Curated route imagery is now reliable and attributed, but runtime presentation still depends on Wikimedia availability and cache behavior.

**Improve by:**

- Move abuse-sensitive limits to a shared atomic store and include account, IP/device risk and action-specific keys.
- Make rate-limit decisions observable without logging raw secrets or precise location.
- Self-host or proxy licensed route assets through a controlled CDN if route cards are release-critical.
- Add image dimensions, decoding/loading hints and a tested branded fallback.

## UX screenshot review

### Confirmed healthy in the tested PWA fixture

- Bottom-navigation icons and labels render on initial load at all four viewport classes.
- The navigation surface sits against the bottom safe area without overlapping the home-indicator allowance.
- No tested screen creates horizontal document overflow.
- Selected navigation state remains visible and consistent.
- Search controls remain reachable in landscape, and the map remains visible behind the search surface.
- Routes adapt to a multi-column tablet/landscape presentation.

### UX improvements visible in the screenshots

1. **Landscape density:** Friends and Ride use a small central column and leave most of the screen unused.
2. **Search recovery:** the location-required state needs a manual search-area fallback and clearer permission guidance, not only “Try location again”.
3. **Routes scanning:** small phones show one dominant card at a time; add a compact list/map toggle or stronger route comparison affordance.
4. **Settings hierarchy:** account and safety-critical controls should remain above lower-frequency preferences, with destructive actions isolated at the end.
5. **Map evidence:** the deterministic blank map fixture should be complemented by a staging test using a restricted provider key; a blank fixture is not evidence of production map availability.

## Recommended delivery order

1. **Safety integration:** movement lock, ride-safe UI, physical-device tests.
2. **Voice vertical slice:** one private ride, real audio, mute/block, reconnect and Bluetooth interruption handling.
3. **Location correctness and scale:** accuracy/freshness contract, SQL spatial/bucket query, shared transitions, load test.
4. **Operational launch baseline:** recovery, retention jobs, backups/restore, monitoring, incident and moderation runbooks.
5. **Realtime transport:** messages, friends, ride roster/location and hazards.
6. **Billing:** only after entitlements can be securely enforced server-side.
7. **UX hardening:** WebKit/native/accessible visual gates, landscape layouts, staged provider checks.
8. **Navigation differentiation:** rider-specific group, hazard and route context around OS-level handoff.

## Release decision

**Current recommendation: do not market or release Rider Comms as a hands-free communications/navigation product yet.** It is suitable for continued controlled testing as a PWA preview and Expo/native development build. A production release should wait for the P0 items, a real-device ride test, production app-link verification files, a restricted Android Maps SDK key and the operational controls described above.
